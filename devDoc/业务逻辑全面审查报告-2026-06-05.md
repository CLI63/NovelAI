## 二、后台任务系统核心逻辑审查

### 2.1 后台任务数据层 (`useBackgroundTask.js`)

**文件位置：** `src/composables/useBackgroundTask.js`

**核心功能：**
- 提供基于 IndexedDB 的后台任务 CRUD 操作
- 定义了 8 种任务类型和 6 种任务状态
- 包含任务恢复、任务统计、任务清理等辅助方法
- 负载清洗函数（`sanitizeBackgroundTaskPayload`）防止 Vue 响应式对象写库

**任务类型：**

| 任务类型 | 代码常量 |
|------|------|
| 章节后处理 | `CHAPTER_POST_PROCESS` |
| 批量章节处理 | `BATCH_CHAPTER_PROCESS` |
| 摘要生成 | `SUMMARY_GENERATION` |
| 伏笔提取 | `FORESHADOWING_EXTRACT` |
| 角色更新 | `CHARACTER_UPDATE` |
| 时间线记录 | `TIMELINE_RECORD` |
| 全本生成 | `FULL_NOVEL_GENERATION` ⭐ |
| 批量章节生成 | `BATCH_CHAPTER_GENERATION` ⭐ |

**任务状态：**
- `pending` → `running` → `completed`/`failed`/`partial`/`paused`

**✅ 优点：**
- 数据层与执行层分离清晰
- 负载清洗机制合理，避免 DataCloneError
- 支持任务恢复（`recoverInterruptedTasks`）

**⚠️ 发现的问题：**
- **`ensureChapterPostProcessTask` 中 `COMPLETED` 状态也禁止重复创建**（第84行）：章节后处理是具有时效性的操作，当章节内容被修改后应该允许重新后处理，但当前逻辑会阻止对已完成的章节重新触发后处理
- **`getAllTasks` 分页逻辑有 bug：** 分页数组反转后没有正确切片，可能导致分页不正确
- **状态更新不原子化：** 并发执行多个任务时，可能出现状态竞争

### 3.2 核心执行引擎 (`useBackgroundTaskPanel.js`)

**文件位置：** `src/composables/useBackgroundTaskPanel.js`

**核心职责：**
- 协调后台任务的执行流程
- 管理任务队列和自动执行机制
- 提供 `autoRunQueue` 和 `flushAutoRunQueue` 实现任务自动排队

**关键状态：**

| 状态 | 来源 |
|------|------|
| `recentTasks` | 从 IndexedDB 读取的后台任务列表（按创建时间倒序） |
| `taskStats` | 各状态任务数量统计 |
| `runningTaskIds` | 当前正在执行中的任务 ID 集合 |
| `autoRunQueue` | 待自动执行的任务队列（内存级） |

**执行函数：**

| 函数 | 说明 |
|------|------|
| `executeTask(task)` | 执行任务的核心函数 |
| `scheduleAutoRun(task)` | 将任务加入自动执行队列 |
| `flushAutoRunQueue()` | 轮询执行自动执行队列 |
| `executeAllPending()` | 执行所有待处理任务 |
| `executeChapterPostProcess(task)` | 执行单个章节后处理 |
| `executeBatchChapterProcess(task)` | 执行批量章节处理 |
| `executeFullNovelGeneration(task)` | 执行全本生成 |
| `executeBatchChapterGeneration(task)` | 执行批量章节生成 |

**事件监听（在 panel 初始化时）：**

```javascript
// onMounted
await recoverInterruptedAutoRunnableTasks() // 恢复中断的任务
await resumePendingAutoRunnableTasks()     // 恢复挂起的任务

// 监听事件
EVENTS.TASK_CREATED       → handleTaskCreated → scheduleAutoRun
EVENTS.TASK_STATUS_CHANGED  → 刷新任务列表
EVENTS.TASK_EXECUTED      → 刷新任务列表
EVENTS.TASK_FAILED        → 刷新任务列表
```

**⚠️ 发现的问题：**

1. **`autoRunQueue` 是模块级全局变量，生命周期存在问题：** 页面刷新后 `autoRunQueue` 会被重置为 `[]`，虽然可以从数据库恢复，但 `autoRunScheduled` 标志也会被重置，可能导致并发调度多个 `flushAutoRunQueue`

2. **`runningSessionIds` 集合内存泄漏风险：** 如果 `executeTask` 在 `try-finally` 之前抛出了未被捕获的异步异常，`runningSessionIds.delete(task.id)` 可能永远不会执行

3. **`resumePendingAutoRunnableTasks` 与 `recoverInterruptedAutoRunnableTasks` 执行顺序问题：** 两个函数都会调用 `scheduleAutoRun`，如果一个任务最开始是 `running` 被恢复为 `pending`，再被 `resumePendingAutoRunnableTasks` 检测到又会再次 `scheduleAutoRun`，虽然不会出大问题但会重复入队

4. **`executeBatchChapterGeneration` 中 `data.result` 的写操作没有原子性：** 在循环中频繁更新 `data.results`，但 `persistBatchGenerationProgress` 会把整个对象写库，可能导致性能问题

### 3.3 全本生成全局控制 (`useGlobalFullNovelGeneration.js`)

**文件位置：** `src/composables/useGlobalFullNovelGeneration.js`

**核心职责：**
- 管理全局全本生成状态（`fullGen`）
- 创建全本生成后台任务
- 从任务快照恢复全本生成状态

**状态：**

| 状态 | 说明 |
|------|------|
| `fullGen` | 通过 `ensureFullGen` 懒加载的 `useFullNovelGeneration` 响应式对象 |
| `visible` | 悬浮面板是否可见 |
| `expanded` | 悬浮面板是否展开 |
| `novelId` | 当前全本生成的小说 ID |
| `currentTaskId` | 当前全局全本生成的任务 ID |

**⚠️ 发现的问题：**

1. **`fullGen` 全局单例模式存在状态污染风险：** 当切换小说重新开始全本生成时，旧的全本生成状态需要被完全重置，但 `ensureFullGen` 不会创建新的实例

2. **`applyTaskSnapshot` 中对任务状态的判断逻辑有 bug：** 第55-56行：
   ```javascript
   if (task.status === 'completed') {
     gen.phase = task.result?.cancelled ? 'cancelled' : 'completed'
   ```
   这里 `task.result?.cancelled` 永远取不到值，因为 `cancelled` 状态会设置更改为 `cancelled` 而非 `completed`

3. **`restoreLatestTask` 只查找第一个符合条件的任务：** 第136-139行的 `find` 只能返回一个任务，如果有多个同时满足条件的任务，可能遗漏某些任务

4. **`syncFromTask` 没有验证 `visible` 设置：** 如果通过外部事件收到 `TASK_CREATED` 时面板尚未初始化完成，`visible` 可能未正确设置

### 3.4 全本生成核心逻辑 (`useFullNovelGeneration.js`)

**文件位置：** `src/composables/useFullNovelGeneration.js`

**核心流程：**

```
start(novelId)
  ├── 加载小说信息
  ├── 重置进度
  ├── 统计已有章节（支持续写）
  ├── 循环生成每一章
  │     ├── 检查暂停/取消 (checkPause)
  │     ├── 获取智能策略 (getStrategyInfo)
  │     ├── 构建上下文 (buildChapterContext)
  │     ├── AI 生成章节
  │     ├── 解析标题和内容
  │     ├── 生成摘要
  │     ├── 保存章节到数据库
  │     ├── 创建后处理任务 (enqueuePostProcessing)
  │     └── 更新进度回调 (_onProgress)
  └── 标记完成/失败/取消
```

**⚠️ 发现的问题：**

1. **`customPrompt` 为空字符串时仍会产生干扰：** 第229行 `if (customPrompt.value.trim())` 条件判断正确，但如果 `customPrompt` 为空，`messages` 中没有额外要求

2. **`pause`/`resume`/`cancel` 的状态安全机制存在高并发下的竞态条件：** 如果多个面板同时触发暂停/继续，可能导致状态不一致。

3. **生成章节出断言失败时不影响后续：** 第237行和第247-249行的 `continue` 意味着某个章节生成失败后，会继续生成下一个章节。这在全本生成场景可能导致**跳章**（中间有个空缺口）。

4. **暂停后恢复不会回到正确的章节上下文：** 当 `checkPause` 返回后，重新生成后的上下文（`recentChapters`, `chapterSummaries` 等）可能不包含上一次生成间隔中生成的内容，可能会影响剧情连续性。

## 四、业务逻辑闭环检查

### 4.1 任务创建 → 执行 → 完成 数据流

```
NovelDetail.vue / ChapterCreate.vue / ChapterList.vue
         │
         │ 调用 createBackgroundTask(taskData)
         │ 并 eventBus.emit(EVENTS.TASK_CREATED, {id, ...taskData})
         ▼
GlobalFullGenerationPanel.vue (onMounted)
         │
         │ 监听 EVENTS.TASK_CREATED
         ▼
useBackgroundTaskPanel.scheduleAutoRun(task)
         │
         │ 加入 autoRunQueue
         │ 调度 flushAutoRunQueue()
         ▼
useBackgroundTaskPanel.executeTask(task)
         │
         │ 根据 task.type 分派到
         │ 不同的执行函数
         ▼
executeFullNovelGeneration / executeBatchChapterGeneration /
executeBatchChapterProcess / executeChapterPostProcess
         │
         │ 执行完成后
         │ updateTask(task.id, {
         │   status: COMPLETED/FAILED,
         │   result/error
         │ })
         │
         │ eventBus.emit(EVENTS.TASK_EXECUTED /
         │   EVENTS.TASK_STATUS_CHANGED /
         │   EVENTS.TASK_FAILED)
         ▼
GlobalFullGenerationPanel.vue
         │
         │ 监听上述事件
         │ → handleTaskLifecycle
         │   → syncFromTask + refreshTasks
         ▼
UI 更新 (面板/列表同步)
```

**✅ 闭环检查结论：数据流完整。**
- 任务创建入库
- 事件广播
- 面板自动监听并调度执行
- 执行后持久化结果
- 事件广播通知各组件更新

**⚠️ 风险点：**
1. 如果 App.vue 重载导致 `GlobalFullGenerationPanel` 被重新挂载，`onMounted` 会重新执行 `recover` 和 `resume` 逻辑，可能会对正在进行的任务重复调度

2. `ChapterList.vue` 也直接 `emit` 了 `TASK_CREATED` 事件，但也通过 `getChapterPostProcessStatus` 维护本地状态，这可能导致**数据源和展示不同步**

---

### 4.2 任务持久化 ↔ 内存状态同步

**✅ 优点：**
- 所有任务状态都通过 `updateTask` 持久化到 IndexedDB
- 面板初始化时从数据库恢复（`recoverInterruptedAutoRunnableTasks`）
- 刷新后能正确恢复到之前的状态

**⚠️ 问题：**

1. **`fullGen` (全局生成器) 状态未频繁持久化，只在 `setOnProgress` 回调时更新：** 如果页面在生成过程中刷新，虽然任务状态可以恢复，但生成器内有多少结果在 `results` 中是不准确的（它依赖实际的 `fullGen.results`，而这些只从任务快照恢复）

2. **`runningSessionIds` 集合内存级：** 页面刷新后清空，在 `recover` 逻辑中没有完全重建（因为它是基于内存集合的）。这可能导致刷新后即使任务实际正在运行，也会认为它是空闲的，从而允许创建新任务

---

### 4.3 全局面板 ↔ 各组件状态一致性

**全局面板中展示的数据来源（computed）：**

| computed | 来源 |
|---|---|
| `phaseLabel` / `subPhaseLabel` | `fullGen.phase` / `fullGen.progress.currentPhase` |
| `recentTaskItems` | `recentTasks`（从 DB 获取，limit=50） |
| `hasTaskActivity` | `taskStats` 中的 pending/running/failed/paused |
| `panelVisible` | `visible.value OR hasTaskActivity` |
| `summaryText` | 基于 `taskStats` 计算 |

**⚠️ 问题：**

1. **`taskStats` 是 `getTaskStats()` 的结果，在 `onMounted` 时才查询：** 如果数据量很大或者时间差，`taskStats` 可能不能及时反映最新的状态

2. **全本生成的 `fullGen` 状态和后台任务的真实执行状态可能出现不一致：** 例如全本生成实际上已经完成，但 `fullGen.phase` 仍然是 `chapters`（因为面板的 `syncFromTask` 没有执行）

---

### 4.4 章节后处理闭环

**触发路径：**
1. `ChapterCreate.vue` 在保存章节后创建后处理任务
2. `ChapterList.vue` 通过按钮手动触发
3. `useFullNovelGeneration.js` 在每章生成后自动创建后处理任务

**执行关联：**

```
enqueuePostProcessing
  ──→ ensureChapterPostProcessTask (检查是否重复)
  ──→ createTask(CHAPTER_POST_PROCESS)
  ──→ eventBus.emit(EVENTS.TASK_CREATED, ...)
  ──→ useBackgroundTaskPanel.scheduleAutoRun
  ──→ executeChapterPostProcess
  ──→ processChapter (8大步骤后处理)
  ──→ 入库
  ──→ eventBus.emit(EVENTS.TASK_EXECUTED)
  ──→ ChapterList/handleTaskStatusEvent → 刷新章节后处理状态
```

**✅ 闭环结论：完整。**

**⚠️ 不足：**
1. `ensureChapterPostProcessTask` 禁止对已完成状态重新创建。一旦内容修改需要重新后处理时，`COMPLETED` 会被阻止
2. 批量后处理任务（`BATCH_CHAPTER_PROCESS`）的内部子任务执行，缺少全局进度聚合

## 五、发现的具体问题清单

### 🔴 严重问题

#### 1. `useGlobalFullNovelGeneration.js` 的 `applyTaskSnapshot` 中 `cancelled` 状态判断逻辑（第55行）
**影响：** 如果一个全本生成被 "取消"，其取消状态被设置为 'cancelled'，但从生命周期流程来看，`syncFromTask` 只有在下面分支才会被触发并被可能变为 completed 的人为阻塞。在实际代码路径中，如果用户点击了"暂停"然后刷新页面，恢复后显示的状态可能不正确。**实际代码有重写逻辑，此问题已经被后续新的 commit 涉及。**

#### 2. `executeBatchChapterGeneration` 未更新最终结果到数据库（第462行）
**影响：** 批量生成完成后的最终数据会作为 result 被包回给 await updateTask，从 `executeTask` 调用后普通 `TASK_STATUS.COMPLETED` update 会写进去（第540行更新 status 和 result），但需要验证 `data` 和 `result` 的字段是否完全覆盖。如果对不上，可能导致面板显示旧数据。

#### 3. `executeFullNovelGeneration` 中 `syncFromTask` + `setOnProgress` + `updateTask` 多重更新可能造成竞态
**影响：** 在全本生成过程中，如果某章生成耗时较长，用户点击暂停，再点击恢复，期间 `onProgress` 回调持续更新任务，如果此时 `syncFromTask` 也更新任务，可能出现写冲突

### 🟡 中等问题

#### 4. `autoRunScheduled` 模块级变量，App 重载后状态丢失
**影响：** 每次刷新页面，`autoRunScheduled` 从 `false` 开始，可能会导致即使队列里有多个待执行的任务，`flushAutoRunQueue` 也会被并行地调度多次

#### 5. 章节生成中某章失败后继续生成下一章（跳章现象）
**影响：** 在 `useFullNovelGeneration.js` 第233行和第243行的 `continue` 会导致中间有章节生成失败而跳过的空洞

#### 6. `onBeforeUnmount` vs `onUnmounted` 事件解绑不一致
**代码：**
```javascript
onBeforeUnmount(() => {
  window.removeEventListener('resize', clampPosition)
  stopDrag()
})
onUnmounted(() => {
  eventBus.off(EVENTS.TASK_CREATED, handleTaskCreated)
  eventBus.off(EVENTS.TASK_STATUS_CHANGED, handleTaskLifecycle)
  eventBus.off(EVENTS.TASK_EXECUTED, handleTaskLifecycle)
  eventBus.off(EVENTS.TASK_FAILED, handleTaskLifecycle)
})
```
**影响：** 事件在 `beforeUnmount` 阶段解绑其实时间差不多，但语义上不一致。更标准的做法是在 `onUnmounted` 阶段统一处理。不过这不是一个 bug

#### 7. `useFullNovelGeneration` 中的 `_onProgress` 只有一个回调
**影响：** 如果同一时刻有多个监听者都想知道进度（例如一个面板要展示，一个全局状态要保存），只有一个 callback 会导致数据丢失

### 🟢 轻微问题

#### 8. `getAllTasks` 的 limit 参数可能无法正确工作
**影响：** `useBackgroundTask.js` 第207行 `getAllTasks` 分页逻辑中，先 `sortBy('createdAt')` 后 `reverse()`，但 `offset`/`limit` 切片是在反转之前还是之后不明确

#### 9. `useBackgroundTask` 中 `TASK_STATUS.PARTIAL` 状态未在流程中使用
**影响：** PARTIAL 状态被定义 but never actively set by the execution engine, currently it's only returned by `executeBatchChapterGeneration`

#### 10. `GlobalFullGenerationPanel.vue` 中 `handleTaskLifecycle` 如果没有 `latestTask` 会用传入的 `task` 做 fallback
**影响：** `task` 对象传入时可能并非最新状态，如果 `recentTasks` 还没有被 `refreshTasks` 更新，`syncFromTask(task)` 会基于过期的数据做快照恢复

## 六、总体评价与建议

### 6.1 架构优点

1. **事件驱动设计合理：** 通过事件总线实现模块间解耦，各触发点和监听点职责清晰
2. **持久化机制健全：** 所有任务都写入了 IndexedDB，支持中断恢复
3. **分级管理：** `useBackgroundTask`（数据层）→ `useBackgroundTaskPanel`（执行层）→ `GlobalFullGenerationPanel`（UI层），职责分离明显
4. **错误边界处理完善：** `executeTask` 的 `try-catch` 包裹了完整的执行流程，失败能正确更新状态

### 6.2 改进建议

1. **统一任务状态机：** 建议为 `fullGen` 和 `backgroundTask` 建立统一的状态机转换规则，避免两者状态不一致
2. **增加执行锁/互斥量：** 针对 `executeTask` 的全局调度增加互斥锁，防止并发调度导致的状态竞态
3. **完善 `autoRunQueue` 的持久化：** 将队列状态也写入 IndexedDB，页面刷新后不会漏掉待执行任务
4. **考虑章节生成失败的重试机制：** 对于 `executeFullNovelGeneration` 和 `executeBatchChapterGeneration` 中的章节生成失败，不要直接跳过，而是增加重试逻辑
5. **监控和日志：** 增加后台任务执行的详细日志和监控指标，方便排查问题
6. **状态同步优化：** 考虑使用 `watch` 监听 `fullGen` 关键状态变化，而不是依赖回调
