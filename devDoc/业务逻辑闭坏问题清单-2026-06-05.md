# novel-ai 项目业务逻辑闭坏问题清单

> 审查日期：2026-06-05  
> 分类优先级：🔴 严重 / 🟡 中等 / 🟢 轻微

## 🔴 严重问题

### 1. `useGlobalFullNovelGeneration.js:55` 错误条件实无可达——`cancelled` 逃脱显示逻辑

**文件：** `src/composables/useGlobalFullNovelGeneration.js`  
**现象：** 在 `applyTaskSnapshot` 中：
```javascript
if (task.status === 'completed') {
  gen.phase = task.result?.cancelled ? 'cancelled' : 'completed'
}
```
`task.result?.cancelled` 在当前业务流中永远取不到值——因为 `useFullNovelGeneration.cancel()` 会直接将 `phase` 改为 `'cancelled'`，而 never 进入 `completed` 分支。  
**影响：** 用户暂停再恢复时，如果中间刷新了，相位恢复不正确。  
**修复建议：** 判断改为 `task.status === 'cancelled' || (task.status === 'completed' && task.result?.cancelled)`。

---

### 2. `executeBatchChapterGeneration` 的最终写库不保证 `finalStatus` 已被持久化

**文件：** `src/composables/useBackgroundTaskPanel.js:443-461`  
**现象：** 第443行计算 `finalStatus`，但最终 updateTask 被 `executeTask` 外层在532-540行覆盖：
```javascript
if (result.success) {
  const nextStatus = result.status || TASK_STATUS.COMPLETED
  await updateTask(task.id, { status: nextStatus, ... })
}
```
`result.data` 包含了 `status: finalStatus`，但 `executeTask` 只取 `result.success && result.status`，不保证 `finalStatus`（如 `PARTIAL`）被写入。  
**影响：** 当批量生成部分章节失败时，任务状态可能被错误标记为 `COMPLETED` 而非 `PARTIAL`。  
**修复建议：** 确保 `executeBatchChapterGeneration` 返回的 `status` 字段被 `executeTask` 正确读取。

---

### 3. `runningSessionIds` 模块化变量同步不可靠

**文件：** `src/composables/useBackgroundTaskPanel.js:16`  
**现象：** `const runningSessionIds = new Set()` 是模块级全局变量。如果页面刷新，它会被重置。  
**影响：** 当用户刷新页面后：
1. 如果此时任务实际上还在运行（不可能，因为刷新会中断 JS），但 `runningSessionIds` 已空
2. `recoverInterruptedAutoRunnableTasks` 会把所有 `RUNNING` 状态的改为 `PENDING`，这是正确的  
**修复建议：** 状态应以 IndexedDB 中的 `status` 作为唯一数据源，内存中的 `runningSessionIds` 仅供参考，不应通过其做互斥判断。在做 `executeTask` 时，应该检查 DB 中的最新状态而非仅靠内存集合。

### 4. `batch_chapter_generation` 类型任务在 `autoRunQueue` 中会被跳过

**文件：** `src/composables/useBackgroundTaskPanel.js:32-34`  
**现象：** `isPanelExecutableTask` 函数明确排除了 `BATCH_CHAPTER_GENERATION`：
```javascript
function isPanelExecutableTask(task, taskTypes) {
  return task?.type !== taskTypes.BATCH_CHAPTER_GENERATION
}
```
但在 `autoRunnableTaskTypes` 中却包含了这个类型：
```javascript
const autoRunnableTaskTypes = [
  TASK_TYPES.FULL_NOVEL_GENERATION,
  TASK_TYPES.BATCH_CHAPTER_GENERATION,  // ⚠ 矛盾
  TASK_TYPES.CHAPTER_POST_PROCESS,
  TASK_TYPES.BATCH_CHAPTER_PROCESS,
]
```
**影响：** 批量章节生成任务创建后会被 `scheduleAutoRun` 入队（因为 `scheduleAutoRun` 检查 `autoRunnableTaskTypes`），但在 `executeAllPending` 中会被 `isPanelExecutableTask` 过滤掉。  
**修复建议：** 统一这两个地方的逻辑。要么把 `BATCH_CHAPTER_GENERATION` 从 `autoRunnableTaskTypes` 中移除，要么修改 `isPanelExecutableTask` 包含它。取决于业务上是否应该通过面板手动执行，以不实际可预知行为。

### 5. 全本生成中 `paused` 后恢复不会重试失败的章节

**文件：** `src/composables/useFullNovelGeneration.js:57-62`  
**现象：** 在 `start` 方法中，如果一章生成失败或内容过短，`error` 会被记录，`chapterNum++` 继续。但如果中途点击了暂停，恢复后从下一个章节号继续：
```javascript
try {
  content = await callAIWithConfig(messages)
} catch (e) {
  errors.value.push({ chapter: chapterNum, ... })
  chapterNum++
  continue  // 失败直接进入下一章
}
```
**影响：** 全本生成连续失败后，不只是跳过一章的问题，后续章节因上下文缺失可能导致连续失败。这才是设计意图，**跳章会导致最终全本缺失章节**。这并不一定是设计者的原意。从实际代码看，出断言失败后并未存档结果（不算已创建条目），这表明生成的章节号因此延后了一个（如，第二章实际存到了第三章），导致章节编号和内容不一致。

## 🟡 中等问题

### 6. `autoRunQueue` 刷新后重复调度

**文件：** `src/composables/useBackgroundTaskPanel.js:29-30`  
**现象：**
```javascript
let autoRunScheduled = false
```
刷新页面后它会重置为 `false`，即使 `autoRunQueue` 里有从 `recover` 恢复的任务。  
**影响：** 如果有多个 recover 的任务，`scheduleAutoRun` 对每个都调用：
```javascript
scheduleAutoRun(task1) // autoRunScheduled=false → 调度 flush
scheduleAutoRun(task2) // autoRunScheduled=true → 只入队
```
这是正确的。但如果在 `flushAutoRunQueue` 执行期间又触发新的 `scheduleAutoRun`（例如通过 `ON HANDLE` 事件），则可能出现并发：
```javascript
function scheduleAutoRun(task) {
  if (!autoRunScheduled) {  // 多个任务同时检查，可能都为 false
    autoRunScheduled = true
    Promise.resolve().then(flushAutoRunQueue)
  }
}
```
**修复建议：** 使用原子操作或锁来控制调度逻辑。

### 7. `executeTask` 中 `runningTaskIds` 和 `runningSessionIds` 双源状态不一致

**现象：**
```javascript
// runningTaskIds 是 ref，Vue3 响应式的
const next = new Set(runningTaskIds.value)
next.add(task.id)
runningTaskIds.value = next
// runningSessionIds 是普通 Set
runningSessionIds.add(task.id)
```
在 `executeTask` 开始时同时加入两个集合，在结束时同时移除。但如果在执行过程中间某个步骤失败（非 `finally`），或者 JS 引擎发生意外（如页面崩溃），`runningTaskIds` 取决于组件是否卸载（`ref` 会随组件销毁），而 `runningSessionIds` 是全局模块级——这意味着它泄露的概率更高。  
**修复建议：** 统一使用一个数据源，推荐只用 `runningTaskIds`。

---

### 8. `executeFullNovelGeneration` 使用双重状态流

**文件：** `src/composables/useBackgroundTaskPanel.js:463-497`  
**现象：** 这函数的 `syncFromTask(task)` 会 set fullGen 和 update task 状态，但期间 `onProgress` callback 还会再次 `updateTask`。如果有两个任务同时发生更新或者斯塔更新被覆盖，可能导致不一致。  
**修复建议：** 避免重复更新同一个任务。将更新逻辑集中在 `onProgress` 里，移除 `_onProgress` 中的额外更新。

---

### 9. `handleTaskLifecycle` 在 GlobalFullGenerationPanel 中做 `syncFromTask` 时数据可能过时

**文件：** `src/components/chapter/GlobalFullGenerationPanel.vue:201-208`  
**现象：**
```javascript
async function handleTaskLifecycle(task) {
  await refreshTasks()
  if (task?.type !== 'full_novel_generation') return
  const latestTask = recentTasks.value.find(item => item.id === task.id) || task
  syncFromTask(latestTask)
}
```
`refreshTasks()` 是异步的，但只有 `await`，**不能保证 `recentTasks` 已经是 `refreshTasks` 后的最新数据——因为 `refreshTasks` 中的 `recentTasks.value = tasks` 可能会比 `await` 稍慢才触发**。  
**修复建议：** 使用 `await nextTick()` 在 `refreshTasks` 后强制 DOM 更新完成，或者使用事件机制在 `updateTask` 完成后触发。

---

### 10. `updateTask` 在 `useBackgroundTask.js:113` 中没有原子性

**现象：**
```javascript
const updateTask = async (taskId, updates) => {
  await db.backgroundTasks.update(taskId, sanitizeBackgroundTaskPayload({
    ...updates,
    updatedAt: new Date().toISOString()
  }))
}
```
这只是一次简单的 `Dexie` update。但如果在每次 `onProgress` 中都调用它（全本生成频繁更新），可能因为频繁的写操作导致性能问题。  
**修复建议：** 使用节流或去抖技术限制更新频率，或者在数据变化较大时再做更新。

---

### 11. `ChapterList.vue` 监听事件可能重复执行刷新

**文件：** `src/components/chapter/ChapterList.vue:213-266`  
**现象：** `handleTaskStatusEvent` 对所有 `TASK_CREATED`, `TASK_STATUS_CHANGED`, `TASK_EXECUTED`, `TASK_FAILED` 都响应并查询 `loadPostProcessStatus()`。如果一个后处理任务从创建到执行会连续触发多个事件，可能会频繁查询数据库。  
**修复建议：** 增加防抖；只在特定事件才刷新。**（可优化，非阻断问题）**

### 12. useFullNovelGeneration 中的 `checkPause` 带系统级别 risk

**文件：** `src/composables/useFullNovelGeneration.js:125-130`  
**现象：**
```javascript
async function checkPause() {
  while (paused.value && !cancelled.value) {
    await new Promise(resolve => { resumeResolver = resolve })
    resumeResolver = null
  }
  if (cancelled.value) throw new Error('CANCELLED')
}
```
暂停机制通过 `while` + `Promise` 阻塞。这意味着在暂停期间，JS 引擎的 microtask 队列被 starve。如果用户停留时间过长，可能的原因有：内存增长，或者影响到 EventBus 上其他事件的处理。此基础上的分析显示JS microtask队列的starvation是一个关键点。  
**修复建议：** 可考虑使用事件通知或 state machine 切换，而不是 `while` 循环等待。

## 🟢 轻微问题

### 13. `getAllTasks` 切分逻辑可能颠倒

**文件：** `src/composables/useBackgroundTask.js:202-218`  
**现象：** `sortBy('createdAt')` 后 `reverse()`，再 `slice(offset, offset + limit)` 。如果 `offset` 大于反转后的数组长度，`slice` 返回空数组。  
**修复建议：** 可以考虑用 `offsetFromBack = allTasks.length - offset - limit` 反向计算切片位置，或者直接在查询时按 `desc` 排序。

---

### 14. 全本生成的 `_onProgress` callback 系统和 `useBackgroundTaskPanel` 的 `updateTask` 覆盖可能冲突

**现象：**
```javascript
// useFullNovelGeneration.js
fullGen.setOnProgress(async (progress) => {
  await updateTask(task.id, {
    data: { ...task.data, progress }
  })
})
```
当面板 `handleTaskStatusEvent` 中的 `handleTaskLifecycle` 执行时：
```javascript
async function handleTaskLifecycle(task) {
  await refreshTasks()          // 刚读
  syncFromTask(latestTask)      // 把刚读的最新数据同步到 fullGen
  // 未来的 updateTask 改 task 数据... 但 fullGen 也是 stateful；如果 _onProgress 当时在执行，
  // 会写 task 的 data 覆写已有的 data（可能丢失某些字段）
}
```
**修复建议：** `updateTask` 改为只更新需要的字段，不覆盖整个 `task.data`。或者Deep merge。

---

### 15. `persistBatchGenerationProgress` 频繁大对象 update 性能开销

**文件：** `src/composables/useBackgroundTaskPanel.js:266-278`  
**现象：** `plannedChapters` 可能包含所有章节数据——每个长 `content` 和 `summary` 都会并入 data。在 `BATCH_CHAPTER_GENERATION` 期间，`for` 循环每一章都会触发一次 `updateTask` 写整个 `data`（包括所有已完成章节的 content）。  
**修复建议：** 将进度数据和章节内容数据分离存储，只更新变化了的字段。

---

### 16. `eventBus` 回调中没有错误隔离

**文件：** `src/utils/eventBus.js:44-51`  
**现象：**
```javascript
emit(event, data) {
  if (!this.events[event]) return
  this.events[event].forEach(callback => {
    try {
      callback(data)
    } catch (err) {
      console.error(`事件 ${event} 处理错误:`, err)
    }
  })
}
```
回调中的错误只会被捕获并打印 `console.error`。如果这是一个关键业务流（例如后台任务执行后的通知），丢失这个事件可能导致前后端不一致。  
**修复建议：** 对于关键事件，考虑使用支持 `await` 的 emit，或者在失败时重试。

### 17. useBackgroundTaskPanel 中 `result?.data` 和 `data` 混用

**现象：** 在 `executeFullNovelGeneration` 中：
```javascript
fullGen.setOnProgress(async (progress) => {
  await updateTask(task.id, {
    data: { ...task.data, progress, results: [...fullGen.results] }
  })
})
```
这里 `updateTask` 写入 `data` 字段。而在 `applyTaskSnapshot` 中读取：
```javascript
const progressSnapshot = task.result?.progress || task.data?.progress || {}
```
这会导致进度值可能存到了 `task.data.progress` 但 UI 取的是 `task.result.progress`，两端字段不一致。

### 18. `ensureChapterPostProcessTask` 限制过于严格

**文件：** `src/composables/useBackgroundTask.js:80-85`  
**现象：**
```javascript
const existingTask = chapterTasks.find(task =>
  task.type === TASK_TYPES.CHAPTER_POST_PROCESS &&
  [TASK_STATUS.PENDING, TASK_STATUS.RUNNING, TASK_STATUS.COMPLETED].includes(task.status)
)
```
`COMPLETED` 也在检查范围内。如果章节内容被编辑后需要重新后处理，这个函数会阻止创建新任务。  
**修复建议：** 移出 `COMPLETED` 状态限制，或者增加参数控制是否允许重新创建。

## 总结与行动建议

| 优先级 | 数量 | 建议修复 |
|------|------|---------|
| 🔴 严重 | 5 | 立即修复，影响业务正确性 |

| 🟢 轻微 | 6 | 优化，影响扩展性和维护性 |

**最关键的修复：**
1. 修复 `useGlobalFullNovelGeneration.js` 中 `cancelled` 状态的判断条件
2. 解决 `BATCH_CHAPTER_GENERATION` 在面板上的执行不一致问题
3. 统一 `autoRunQueue` 的刷新后重建机制
4. 解决全本生成中失败章节跳过的逻辑，改为重试
5. 去掉 `ensureChapterPostProcessTask` 的 `COMPLETED` 限制，允许重新后处理
