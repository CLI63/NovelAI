## 方案一：全本流水线生成（P0）

### 现状问题

当前工作流为多步手动操作：

```
创建小说(输入创意) → 生成大纲 → 手动保存
→ 跳转详情页 → 点击生成章节 → 设置范围 → 逐个/批量生成
→ 每章生成后 → 前往任务中心 → 手动执行后处理
```

一部 30 章小说需要数十次手动操作，流程割裂。

### 目标

将以上步骤压缩为**一次点击**：

```
输入创意 → 生成大纲 → 用户确认 → 点击「一键生成全本」
→ 系统自动完成：逐章提纲 → 逐章内容生成 → 后处理 → 交付
```

### 核心改动

| 模块 | 改动内容 |
|---|---|
| `NovelCreate.vue` | 新增「保存并一键生成全本」按钮 |
| `useFullNovelGeneration`（新） | 编排全本生成流程：提纲 → 生成 → 后处理 |
| `FullGenerationProgress`（新） | 全流程进度 UI，支持暂停/继续/取消 |
| 各 DAO | 已有，无需改动 |

### 流程设计

```
用户点击「一键生成全本」
  ↓
保存小说到 IndexedDB
  ↓
[进度 5%] 生成所有章节的详细提纲（逐章调用 AI）
  ↓
用户确认提纲（可选） / 或直接继续
  ↓
[进度 5%-85%] 逐章生成内容（流式输出，实时展示）
  ├─ 每章生成完毕后自动保存
  ├─ 自动执行后处理（摘要、伏笔、角色更新、时间线）
  └─ 支持暂停/继续、断点续传
  ↓
[进度 85%-100%] 全本后处理收尾
  ↓
[完成] 跳转至阅读器
```

### 关键技术选型

- **状态管理**：使用 Pinia + composable 响应式状态（沿用项目风格）
- **持久化**：生成进度存入 IndexedDB `generationTasks` 表（已有），支持页面关闭后恢复
- **流式输出**：复用现有 `callAIStream` + `StreamOutput` 组件
- **断点续传**：复用 `useResumeGeneration` 逻辑

## 方案二：并行章节生成（P1）

### 现状问题

当前批量生成是**逐个串行**调用 API。一部 30 章的中篇小说，平均每章生成 30-60 秒，总耗时 15-30 分钟。用户需要长时间等待。

### 优化思路

#### 2.1 非依赖章节并行

分析章节之间的**依赖关系**：
- 若章节 A 和章节 B 发生在不同视角/地点/时间线，且无直接因果，则可并行生成
- 同一情节线的连续章节仍需串行（保证连续性）

```
串行模式：  第1章 → 第2章 → 第3章 → 第4章 → ...
并行模式：  第1章 ──→ 第2章
              ├──→ 第3章（同时）
              └──→ 第4章（同时，B线）
```

#### 2.2 多 API Key 轮询

- 利用已支持的 4 个厂商 API 同时生成不同章节
- 同一个厂商也可配置多个 Key 做负载均衡
- 自动处理速率限制（rate limit）和退避

#### 2.3 并发控制

- 可配置最大并发数（1-5），默认 2
- 失败自动重试（已有 `callAIWithRetry`）
- 并发章节的上下文各自独立维护

### 预估收益

- 30 章小说：串行 ~20分钟 → 并行(3路) ~7分钟
- 60 章长篇小说：串行 ~40分钟 → 并行(3路) ~14分钟

## 方案三：小说圣经——超长上下文策略（P1）

### 现状问题

当前 `contextBuilder.js` 携带最近 3 章内容 + 其他章节摘要。这对**前后呼应的长篇小说**仍然不够：
- 第 20 章需要引用第 5 章铺设的伏笔
- 角色的成长弧光需要在全本范围内保持一致
- 世界观细节（地名、能力设定）容易产生前后矛盾

### 方案：自动维护「小说圣经」

#### 核心概念

「小说圣经」是一份由 AI 在每章生成后**自动更新的结构化知识文档**，取代传统的滑动窗口上下文。

#### 圣经包含的内容

| 板块 | 内容示例 | 更新时机 |
|---|---|---|
| **角色状态快照** | 每个角色：当前位置、状态、实力等级、人际关系变化 | 每章生成后 |
| **伏笔清单** | 已铺设待回收的伏笔（按优先级排序） | 每章生成后（已有 `FORESHADOWING_EXTRACT`） |
| **关键时间线** | 重要事件及发生章节 | 每章生成后（已有 `TIMELINE_RECORD`） |
| **世界观词典** | 地名、能力、组织等专有名词的准确定义 | 创建时 + AI 检测到新概念时 |
| **写作备忘录** | 风格偏好、特定描写要求、待处理事项 | 用户设定 + 自动积累 |

#### 上下文组装策略

```
生成第N章时：
  ├─ 小说圣经（精简版，~2000 tokens）—— 代替滑动窗口
  ├─ 最近 2 章完整内容（保证行文连贯）
  ├─ 本章提纲
  └─ 当前章节涉及的角色/伏笔详细状态
```

#### 实现方式

- **存储**：在 IndexedDB 中新增 `novelBibles` 表，每部小说一条记录
- **更新**：将已有 `BACKGROUND_TASKS` 中的 `SUMMARY_GENERATION`、`FORESHADOWING_EXTRACT`、`CHARACTER_UPDATE`、`TIMELINE_RECORD` 的结果合并为圣经更新
- **查询**：`contextBuilder.js` 新增 `buildBibleContext()` 方法

## 方案四：全本质量扫描（P2）

### 目标

整部小说生成完成后，一键运行多维度质量检查，自动标记并修复问题。

### 检查项

| 检查项 | 方法 | 严重程度 |
|---|---|---|
| **角色一致性** | 检查角色名称、性格描述、能力设定是否前后矛盾 | 高 |
| **时间线冲突** | 检测事件发生顺序是否合理，时长是否一致 | 高 |
| **伏笔回收** | 检查已铺设的伏笔是否在承诺的时间点得到回收 | 高 |
| **情节漏洞** | AI 检测逻辑矛盾、因果断裂 | 中 |
| **风格一致性** | 评估各章节语言风格、语气、视角是否统一 | 中 |
| **字数均衡** | 检查各章节篇幅是否差异过大（超出均值 ±50%） | 低 |
| **敏感内容** | 基于现有 `useSensitiveWords` 扫描全本 | 低 |

### 实现方式

- **新增 `useFullNovelQualityCheck` composable**：遍历所有章节，逐项检查
- **检查报告**：生成结构化报告，按严重程度分组，可定位到具体章节和段落
- **自动修复**：对角色不一致、伏笔未回收等确定性高的问题，自动触发 AI 修复

### 依赖的现有模块

- `useQualityCheck` — 单章质量检查
- `useCoherenceScore` — 连贯性评分
- `useSensitiveWords` — 敏感词检查
- `ConflictDetector`（OutlineEditor 内）— 情节冲突检测

## 方案五：一键导出整书（P2）

### 目标

将整部小说导出为通用电子书格式，实现「生产即交付」。

### 支持格式

| 格式 | 特点 | 适用场景 |
|---|---|---|
| **EPUB** | 标准电子书格式，支持目录、元数据、CSS 样式 | 主流阅读器（iBooks、Kindle、微信读书） |
| **PDF** | 固定排版，支持自定义样式 | 打印、分享 |
| **Markdown** | 纯文本，易于二次编辑 | 作者自留 |
| **TXT** | 纯文本，兼容性最强 | 极简需求 |

### 导出内容结构

```
封面（书名 + 作者 + 简介）
  → 目录
  → 前言/序（可选）
  → 各章节正文
  → 后记/附录（可选）
```

### 技术方案

- **EPUB 生成**：使用 `epub-gen` 或 `jszip` 手动构建 EPUB（本质是 ZIP + XHTML）
- **PDF 生成**：使用 `html2pdf.js` 或 `jspdf`
- **前端实现**：所有处理在浏览器端完成，无需后端

## 方案六：端到端一键生成——终极体验（远期）

### 定位

将 P0-P5 的所有能力整合为一个完整的「懒人模式」：

```
用户输入：一句话创意 或 详细设定文档
         ↓
系统全自动执行：
  生成大纲 → 生成章纲 → 生成全文 → 后处理 → 质检 → 导出
         ↓
用户回来时：整部小说已就绪，可直接阅读或下载 EPUB
```

### 关键体验设计

- **后台生成不阻塞**：用户可关闭页面，进度通过 IndexedDB 持久化
- **通知机制**：生成完成时可通过浏览器通知 API（`Notification API`）提醒用户
- **渐进式呈现**：已完成的章节可即时阅读，无需等待全本完成
- **手动干预点**：用户可预设干预节点（如「提纲生成后暂停，让我审核」）
