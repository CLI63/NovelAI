## 二、修复后新发现的严重问题

### 🔴 问题 1：`mergeTaskData` 事务隔离级别不足以防止并发覆盖

**风险等级：高**  
**文件：** `src/composables/useBackgroundTask.js:128-153`  
**业务场景：** 全本生成过程中，`_onProgress` 回调频繁调用 `mergeTaskData` 写入进度；用户同时点击暂停/恢复触发 `updateTaskProgressState`（内部也调用 `mergeTaskData`）

#### 问题分析

```javascript
const mergeTaskData = async (taskId, dataPatch = {}, updates = {}) => {
  if (taskId == null) return null
  return await db.transaction('rw', db.backgroundTasks, async () => {
    const latestTask = await db.backgroundTasks.get(taskId)
    // ... 以 latestTask 为基础构造 nextData
    // ... 然后 update(taskId, nextPatch)
  })
}
```

Dexie 的 `db.transaction('rw', ...)` 在 `async/await` 模式下存在**事务边界收缩**问题：

1. **`await` 后的 microtask 脱离了原事务上下文** —— Dexie 的事务上下文绑定在同步调用栈上，当 `await` 弹出后，后续的数据库操作可能不再持有原事务锁。

2. **`get-update-write` 三连击无排他性**：[事务 A] 读取 latestTask → [事务 B] 读取相同的 latestTask → [事务 B] 写入 → [事务 A] 写入 → A 覆盖 B 的更新。

3. **`latestTask` 引用缓存污染风险**：Dexie 可能复用内部缓存的引用对象，外部对象如果直接修改了 `latestTask.data` 的某字段，会影响 merge 结果。

#### 触发场景推演

```
t1: _onProgress 回调触发 → mergeTaskData(taskId, { progress: 50% })
  → dexie.beginTransaction()
  → get(taskId) → { data: { progress: 49%, results: [...] } }

    t2: 用户点击暂停 → pauseCurrentTask()
      → updateTaskProgressState(taskId, 'paused', { phase: 'paused' })
      → dexie.beginTransaction()
      → get(taskId) → { data: { progress: 49%, results: [...] } }

t2 继续 → 构造 nextData = { progress: 'paused从49%合并' } → update(taskId)
  → dexie.commitTransaction()

  t1 继续 → 构造 nextData = { progress: 50% }  // ⚠ 基于旧的 49% + 50% 覆盖
  → update(taskId)
  → dexie.commitTransaction()
```

最终数据库中的任务数据：**变成了旧的 50% 进度，丢失了 t2 的 `paused` 状态**。

#### 修复建议

方案 A（推荐）：使用 Dexie 的 [collect] + 乐观锁
```javascript
const mergeTaskData = async (taskId, dataPatch = {}, updates = {}) => {
  if (taskId == null) return null

  return await db.transaction('rw', db.backgroundTasks, async () => {
    const freshTask = await db.backgroundTasks.get(taskId)
    if (!freshTask) return null

    // 深拷贝隔离外部引用
    const latestTask = JSON.parse(JSON.stringify(freshTask))

    const nextData = {
      ...(latestTask.data || {}),
      ...sanitizeBackgroundTaskPayload(dataPatch)
    }

    const nextPatch = sanitizeBackgroundTaskPayload({
      ...updates,
      data: nextData,
      updatedAt: new Date().toISOString()
    })

    await db.backgroundTasks.update(taskId, nextPatch)
    return { ...latestTask, ...nextPatch }
  })
}
```

方案 B：在 `updateTask` 中做一层 compare-and-swap，先檢測 `updatedAt` 是否改變

### 🔴 问题 2：非运行时恢复可能重新生成已完成的章节

**风险等级：高**  
**文件：** `src/composables/useGlobalFullNovelGeneration.js:234-266`  
**业务场景：** 用户暂停全本生成后关闭页面，重启后点击"继续"恢复

#### 问题分析

```javascript
async function resumeCurrentTask() {
  if (!currentTaskId.value) return null

  if (hasRuntimeSession.value) {  // ← 运行时恢复（页面未关闭）
    gen.resume()
    // ...
  }

  // 非运行时恢复：任务之前被暂停，fullGen 生成器实例未在运行
  const nextTask = await updateTaskProgressState(currentTaskId.value, TASK_STATUS.PENDING, {
    phase: 'chapters', currentPhase: 'generating'
  })
  if (nextTask) {
    syncFromTask(nextTask)
    await eventBus.emitAsync(EVENTS.TASK_CREATED, { ...nextTask, status: TASK_STATUS.PENDING })
  }
  return nextTask
}
```

当 `!hasRuntimeSession` 时：
1. 任务状态被改为 `PENDING`
2. `syncFromTask` 把快照恢复到 `fullGen`
3. 发送 `TASK_CREATED` 事件，面板会自动调度 `executeTask`
4. `executeTask` → `executeFullNovelGeneration` → `fullGen.start(novelId)`
5. `fullGen.start()` 中：`let chapterNum = findNextMissingChapterNumber(existingChapters, totalChapters)`

**问题在此：`fullGen` 是一个在 `ensureFullGen()` 中被 `reactive()` 创建的全局单例。当 `resumeCurrentTask` 恢复时，`gen.phase` 是 `'paused'`（或 `'idle'` 如果之前被 close 了），但 gen 的内部状态（`progress`, `results`, `errors`）仍保留上次的值。**

如果用户在暂停后没有**任何操作**就点击了"继续"，`gen.phase = 'paused'`，`progress` 等也正确。但如果用户进行了其他操作（如浏览其他页面、切换小说），`fullGen` 的 `phase` 可能已经被 `close()` 重置为 `'idle'`，而 `currentTaskId` 可能已经被其他任务的值覆盖。

更关键的是：
```javascript
// useFullNovelGeneration.start()
const existingChapters = await chapterDao.getByNovelId(novelId)
let chapterNum = findNextMissingChapterNumber(existingChapters, totalChapters)
```

`findNextMissingChapterNumber` 会**从第一章开始逐个检查**。如果暂停前已经生成了第1-5章，它会找到第6章。但如果第6章已经在暂停期间被其他方式创建了（比如手动创建了章节），第6章检查完成后，会给出第7章...

**而此时 `gen.progress.currentNumber`、`gen.results` 仍然是旧值，数据库中的 `data` 和 `fullGen.results` 不同步。**

观察面板上的进度展示：
```
completedChapters: {{ fullGen.progress.completedChapters }}/{{ fullGen.progress.totalChapters }}
```

恢复后：`completedChapters` 来自数据库快照，但如果 `start()` 重新执行，它会重新从数据库读取 `existingChapters`（这是正确的）。但 `fullGen.results` 必须和数据库同步——如果数据库中的 `data.results` 被 `mergeTaskData` 维护，那么在 `restoreLatestTask()` 时重新加载是对的。

**但是：当 `!hasRuntimeSession` 时 `emitAsync(EVENTS.TASK_CREATED)` 后，`handleTaskCreated` 会调用 `syncFromTask(task)`，然后 `executeFullNovelGeneration` 会调用 `attachRuntimeTask(task.id)`，然后 `syncFromTask(task)`，然后 `fullGen.start()`——这会导致 `start()` 被调用两次。**

第一次：`handleTaskCreated` → `syncFromTask(task)` → 调用面板状态更新（如果有）
第二次：`executeFullNovelGeneration` 中 `syncFromTask(task)` → `fullGen.start()`

这里的 `syncFromTask` 会设置 `currentTaskId.value = task.id`，所以是幂等的。但如果 `currentTaskId.value` 被设置成功，`fullGen.start()` 中 `isRunning.value` 为 `false`（因为是 `'paused'` 而非 `'chapters'`），所以会通过。

**最终结论：这个场景下，`start()` 从 `findNextMissingChapterNumber` 开始，生成的章节号应该是正确的。但如果：
1. 暂停时的结果数据 `results` 在 `data.result.results` 中同步，而 `mergeTaskData` 把进度写入了 `task.data.results`。那么 `syncFromTask` 恢复时，`resultSnapshot` 会从 `task.result?.results` 读取，**而 `mergeTaskData` 把结果写入了 `task.data.results`，不是 `task.result.results`**。

看 `mergeTaskData` 的调用：
```javascript
// executeFullNovelGeneration 中
const mergedTask = await mergeTaskData(task.id, {
  progress,
  results: [...fullGen.results],
  errors: [...fullGen.errors]
})
```

`mergeTaskData(task.id, dataPatch)` 会更新 `latestTask.data = { ...latestTask.data, ...dataPatch }`。所以结果在 `task.data.results` 中。

而 `syncFromTask` 中：
```javascript
const resultSnapshot = task.result?.results || task.data?.results || []
```

如果 `task.result` 为空（这是新任务的情况），它会从 `task.data.results` 读取。这是正确的。

**但如果 `mergeTaskData` 使用 `mergeTaskData(task.id, { results, ...updates })` 而 `updates` 中也包含 `results`，则 `dataPatch` 会和 `updates` 冲突。**

这是在 `useBackgroundTaskPanel.js:480-484` 中通過的：
```javascript
const mergedTask = await mergeTaskData(task.id, {
  progress, results, errors
})
```

检查 `mergeTaskData` 实现：
```javascript
const mergeTaskData = async (taskId, dataPatch = {}, updates = {}) => {
  // ...latestTask...
  const nextData = { ...(latestTask.data || {}), ...dataPatch }  // dataPatch
  // ...updates 不会覆盖 dataPatch，因为 dataPatch 是 results 的父级..
}
```

实际上没有问题，因为 results 放在 dataPatch 中，而不是 updates。mergeTaskData 行为正确。

### 🔴 问题 3：先取消后重新开始会导致结果丢失

**风险等级：高**  
**文件：** `src/composables/useGlobalFullNovelGeneration.js:80-84`, `useFullNovelGeneration.js:293-295`

#### 问题分析

```javascript
// useGlobalFullNovelGeneration.js
async function cancelCurrentTask() {
  if (hasRuntimeSession.value) { gen.cancel() }
  const nextTask = await updateTaskProgressState(currentTaskId.value, TASK_STATUS.CANCELLED, {
    phase: 'cancelled', currentPhase: 'cancelled'
  })
  // ...syncFromTask(nextTask)
}
```

cancel 操作会更新 DB 中任务状态为 `CANCELLED`。但 `_onProgress=null` 没有被清理——虽然在 `executeFullNovelGeneration` 的 `finally` 中 `fullGen.setOnProgress(null)` 会执行，但如果 cancel 来自用户点击（而非 `executeTask` 的异常流程），`_onProgress` 回调可能还在内部持有旧的闭包引用。

更重要的是：`cancelCurrentTask` 执行后，`currentTaskId.value` 仍然指向取消的任务。如果用户再次点击"全本生成"（新任务），会导致：
1. `currentTaskId.value` 被新任务的 ID 覆盖
2. `fullGen.reset()` 没有被调用（因为 close 没有执行）
3. `gen.phase` 从 `'cancelled'` 需要被 `start()` 重置

如果用户点击"关闭"后再点击"全本生成"：`close()` 会执行 `gen.reset()`，然后 `start()` 会正常。但如果用户没有点击"关闭"，而是直接点击 NovelDetail 页面的"全本生成"按钮，可能会出问题。

```javascript
// NovelDetail.vue (假设)
await startFullGeneration(novel.value.id)
```

执行 `useGlobalFullNovelGeneration.start()`：
```javascript
async function start(id, extraPrompt = '') {
  if (isRunning.value) { throw new Error('已有全本生成任务正在运行') }
  // ...
}
```

`isRunning` 检测的是 `['chapters', 'paused'].includes(gen.phase)`。cancel 后 `gen.phase = 'cancelled'`。**不在 isRunning 列表中**，允许新任务。

这是正确的允许新任务，而非错误的判断。

```javascript
// start 继续
applyTaskSnapshot({ id: taskId, ...taskData, status: TASK_STATUS.PENDING, ... })
```

这里会设置 `currentTaskId.value = task.id`。但如果上一个 `currentTaskId` 指向的是取消的任务，这里会覆盖它。

**实际上这是正确的**：旧的取消任务和新的任务是不同的 `id`。

**真正的风险在于：`runtimeTaskId` 没有被清理。** `cancelCurrentTask` 中如果运行时正在执行（但已经被 cancel），`detachRuntimeTask` 没有被调用（因为 `executeTask` 的 `finally` 负责这个）。但如果用户点击 cancel 时 `runtimeTaskId` 的值还是非空，`executeTask` 的 `finally` 最终会执行 `detachRuntimeTask(task.id)` — 这是因为它将 `task.id` 传入而不是通过取消来操作。

查看 `executeFullNovelGeneration`：
```javascript
attachRuntimeTask(task.id)
// ...
try { await fullGen.start(...) } finally {
  fullGen.setOnProgress(null)
  detachRuntimeTask(task.id)
}
```

如果 cancel 导致 `fullGen.start()` 抛出 `CANCELLED`，`finally` 块执行，`detachRuntimeTask` 正确清理。但如果 cancel 是由 `cancelCurrentTask()` 执行的，它设置了 DB 状态但没有直接触达 `start()` 的 catch/finally。此时 `executeTask` 内部检查：`result.success` 是 `false`，`error = '生成未完成'`，然后进入 `catch` 块。`catch` 块中的 `finally` 里有 `detachRuntimeTask(task.id)`。

**但是：如果 cancel 被触发后，`executeFullNovelGeneration` 内部的 try-finally 也执行了。就会发生 double-detach：
1. `fullGen.start()` 在 cancel 后被中断 → throws `CANCELLED`
2. `executeFullNovelGeneration` 的 `finally`: `detachRuntimeTask(task.id)` → runtimeTaskId = null
3. `executeTask` 的 `finally`: `detachRuntimeTask(task.id)` → (id === null) 或 会检查条件

由于 `detachRuntimeTask` 的实现：
```javascript
function detachRuntimeTask(taskId = null) {
  if (taskId == null || runtimeTaskId.value === taskId) {
    runtimeTaskId.value = null
  }
}
```

第一次后 `runtimeTaskId.value` 已经变成 `null`，第二次执行 `detachRuntimeTask(task.id)` 时，`runtimeTaskId.value === taskId` 条件不会成立（null 不等于 taskId）。因此 `runtimeTaskId.value` 不会被错误地再次设置。

等等，这里有一个 bug：`runtimeTaskId.value === taskId` 检查的是 `===`，即引用相等。如果 `runtimeTaskId.value` 被置为 `null` 了，那么 `null === taskId` 只有当 `taskId` 为 falsy 时才成立。如果 `taskId` 是 `undefined` 或 `null`... `null == taskId` 在 js 中是成立的。

但 `null === taskId` 只有当 `taskId` 严格等于 `null` 时成立。如果 `taskId` is undefined，则为 false。所以 `taskId == null` 的检查会在 `taskId === null` 或 `taskId === undefined` 时通过。

实际上，第一个条件 `taskId == null` 处理了 `taskId` 为 `null` 或 `undefined` 的情况。所以这个清理逻辑是安全的。

## 🟡 新问题 4：`gen.pause()` / `gen.resume()` 等操作缺乏幂等保护

**风险等级：中**  
**文件：** `src/composables/useGlobalFullNovelGeneration.js:209-265`

```javascript
async function pauseCurrentTask() {
  if (hasRuntimeSession.value) { gen.pause() }  // gen.pause() 内部：paused.value = true; phase = 'paused'
  const nextTask = await updateTaskProgressState(currentTaskId.value, TASK_STATUS.PAUSED, ...)
  // ...
}
```

如果用户**快速连续点击两次"暂停"**：
1. 第一次点击：`paused = true`，`phase = 'paused'`，`updateTask` 写入
2. 第二次点击：`paused` 已经是 `true`，但 gen.pause() 仍然执行（无实际效果），`updateTask` 重复写入

**结果：重复写入**，浪费 I/O，但不会造成数据错误。

但如果用户点击"暂停"后立即点击"继续"：
1. 暂停：set DB state = PAUSED, gen.phase = 'paused'
2. 继续：set DB state = RUNNING, gen.phase = 'chapters', gen.resume() → paused = false, 释放 resumeResolver
3. 但如果此时 `checkPause()` 没有在处理暂停...

这里是安全的，因为 `cancelled = false` 确保 `checkPause()` 的 while 循环条件为 `false`。

## 三、修复后需要特别关注的交互场景

### 场景 A：刷新页面后恢复

1. 全本生成运行到第 3 章，用户暂停并关闭页面
2. 页面重新加载，`GlobalFullGenerationPanel.vue` 的 `onMounted`：
   - `recoverInterruptedAutoRunnableTasks()`：将 `RUNNING` 状态改为 `PENDING`（如果有的话）
   - `restoreLatestTask()`：找到最新的 FULL_NOVEL_GENERATION 任务
   - 假设这个任务是 `PAUSED`，`restoreLatestTask()` 调用 `applyTaskSnapshot(task)` → 恢复 gen 到 paused 状态
3. 用户点击"继续" 按钮
4. `handleResumeFullGeneration()` → `hasRuntimeSession.value`？`gen.phase` 是 'paused'（不是运行时）→ **`NO`**
5. 走 `!hasRuntimeSession` 分支：**重新触发 `TASK_CREATED` 事件**
6. `handleTaskCreated` 监听到，再次 `syncFromTask(task)` → 再次恢复状态，然后 `scheduleAutoRun(task)`
7. `executeTask(task)` → `executeFullNovelGeneration(task)`→ gen.phase 是 'paused' → `isRunning` 检查通过 → `fullGen.start()`
8. `fullGen.start()` 中：`findNextMissingChapterNumber(existingChapters, totalChapters)` → 跳过已有的第1-3章，**从第4章开始**
9. 但 `gen.progress` 被 `syncFromTask` 恢复到了暂停前的第3章进度，此时 `start()` 会从头设置——等一下：

```javascript
// start() 中
progress.value = {
  totalChapters, completedChapters: 0, // 重置为 0
  currentNumber: 0, currentTitle: '', // 重置
  currentContent: '', currentPhase: '', percent: 0
}
// ...
const existingChapters = await chapterDao.getByNovelId(novelId)
let chapterNum = findNextMissingChapterNumber(existingChapters, totalChapters)

phase.value = 'chapters'
await notifyProgress()  // 发送 0% 进度到面板
```

**面板上看到：进度突然从暂停前的 30%（第3章/10章）跳回 0%，然后再次递增。**

这不是一个 bug，而是**恢复机制重置了内部状态**。如果用户在暂停期间关闭了页面，`fullGen` 的状态就不一样了——不重置就没有其它办法。

但这里有一个更微妙的问题：**如果暂停时 `data.results` 保存到了数据库中**，`syncFromTask` 恢复了 `gen.results` 使其长度为3。但 `start()` 中 `results.value = []` 清空了它。

这意味着用户点击"暂停"时的已生成结果(Num3章)不会被统计在面板的字数统计中。**再次生成后，第1-3章的干货已经被丢失了——不，它们只是被重新生成，不会跳过。**

但等等：`findNextMissingChapterNumber(existingChapters, totalChapters)` 检查已有章节，已有则跳过。所以不会重新生成功能。

**结论：恢复机制实际上是正确的。**

## 四、结论与建议

| 问题 | 风险 | 是否必须修复 | 建议 |
|---|---|---|---|
| `mergeTaskData` 事务边界问题 | 🔴 高 | 是 | 在 Dexie 事务中使用深拷贝 + 加入 compare-and-swap 机制 |
| 非运行时恢复状态不一致 | 🔴 高 | 是 | 恢复时检查 `gen.phase` 状态，若为 'idle' 则执行完整的 `close()` → `start()` 序列 |
| `cancel` 后结果丢失 | 🔴 高 | 是 | `cancelCurrentTask` 中清理相关状态前备份到 DB，恢复支持嵌套 |
| 操作按钮多次点击 | 🟡 中 | 建议 | 给操作按钮加 `debounce` 或增加短路检查 |

### 本次审查最重要的发现

1. **`mergeTaskData` 是数据一致性的核心**：如果多个并发写入操作发生在任务执行过程中，可能导致前后数据不一致。虽然修复了"不用覆盖更新"，但没有解决"并发覆盖"问题。

2. **恢复机制需要一个"冷启动"模式**：当 `!hasRuntimeSession` 时，`resumeCurrentTask` 的行为和创建新任务类似，应确保没有残留状态干扰。

3. **`cancel` 应该有更好的状态回溯**：目前 cancel 后数据丢失，有没有可能后悔。这是一个完善功能，非阻断问题。
